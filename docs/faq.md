# Hardwise 常见技术问题

> 这份 FAQ 回答关于 Hardwise 设计取舍的六个高频问题。所有数字都可以用
> README 里的命令在公开数据上复现。

## Q1. 这个工具帮硬件工程师省了哪一步？

省的是评审前后的"搬运链"：在原理图、BOM、规格书、引脚定义和检查清单之间
反复查证、对位号、整理证据、写结论。

Hardwise 把这条链整理成评审工作台：导入网表 + BOM 后自动建立器件台账，跑
确定性检查，把结果分成"必须修 / 人工确认 / 检查已满足"三类队列，每条结论
带证据出处。工程师省掉的是查位号、对引脚、整理证据、排除模型胡编对象的
时间；**最终是否接受每条意见，仍由人来判断**。

确定性检查的选型原则：优先覆盖人工评审里最常因人力成本被整体放弃的
体力活——例如逐 pin 对照规格书核对 NC 处理。人工因成本放弃的检查，
恰是自动化回报最高的。

它不替代硬件工程师下判断，也不宣称大模型可以独立评审完整硬件设计。

## Q2. 输入是什么，输出是什么？

**输入（全部公开数据）：**

- Cadence/Allegro 导出的原理图网表（Telesis 单文件或 PST 三件套）+ 导出 BOM
  （CSV/TSV/Cadence `.BOM`/窄列 `.xlsx`）——工作台主路径
- 可选 Capture pin-table CSV——补充网表/BOM 没有的 pin electrical type、
  NC marker 和页面位置；当前只作为 R008/R009/R010 的 L1 review task 来源，
  并在工作台/导出资料中汇总 accepted findings、rejected unknown refdes 和
  affected refdes
- 可选 review-package manifest——记录 schematic PDF、ERC/DRC report、checklist
  和 review notes 等导出证据包的文件名、路径、hash 和缺失状态；只证明评审
  资料是否齐备。缺必需文件或 hash mismatch 会显示为 package-status manual
  gap，不解析成电气结论，也不替代正式签核
- 可选 document-index CSV——可随 live import 一起上传；只按 BOM identity 汇总
  已审核公开资料覆盖，原始 index row 保持 L3，直到页码级检索或 reviewed profile
  支撑更强的证据等级
- KiCad 工程目录（`.kicad_sch` + `.kicad_pcb`）——规则评审与回归基线路径
- 公开规格书 PDF/HTML + 人工审核过的结构化器件档案（`DatasheetProfile`）
- 可选 `DATASHEETS_API_KEY`——本地候选查询只对 MPN-like、未命中文档索引的
  器件组做低流量检索；`build-document-index-candidates --datasheets-com`
  只在"规范化 MPN 精确一致 + 单一命中 + 有直接 PDF URL"时把 document row
  标成 `approved`。这个批准只表示资料覆盖行可进入 reviewer 工作台，不下载 PDF，
  不验证页码级参数，也不改变 PASS/WARN/ERROR
- 检查清单规则（`data/checklists/sch_review.yaml`）

**输出：**

- 三栏评审工作台（本地服务或离线单文件 HTML），含器件队列、验证明细、
  证据出处和 AI 助手问答轨迹
- 六路 evidence-package completeness：netlist/PST、BOM、profile + deterministic
  validation、document index、Capture pin table、review-package artifacts。每一路
  保留自己的 components/refdes/BOM groups/findings/rows/artifacts 单位，不合成
  总分；顶层 `electrical_verdict=not_applicable`
- Markdown/HTML 评审报告与可导出的评审反馈清单
- SQLite/PostgreSQL 结构化存储与运行轨迹台账

公开演示数字：mixed controller 样例 25 个器件 / BOM 全配 / 22 行确定性验证 /
通过-警告-错误 = 5-13-4 / 3 行人工缺口；KiCad `pic_programmer` 121 个器件 /
77 个 NC 引脚 / 19 个显式 schematic-side 命名网络 / 29 条带证据评审发现。
pin-table 检查进入工作台队列；项目级 pin-table summary 会显示 accepted /
rejected unknown-refdes / affected-refdes 覆盖状态，但不改写这组
PASS/WARN/ERROR 总账。
review-package manifest 进入工作台/导出资料的 evidence package summary，
missing required 或 hash mismatch 会显示为 package manual gap；但不生成
PASS/WARN/ERROR，也不替代评审签核。
完整 mixed-controller 证据输入会分别显示 25 个 registry components、BOM
25/25 refdes clean、ready profile 9/25 components、deterministic validation
22/25 components、public document 4/15 BOM groups，以及独立的 pin-table / artifact
状态；这些分母不会互相混算。
`document-candidate-smoke` 在同一个 mixed controller 样例上生成 8 行资料候选；
无直接 URL 的候选不会伪装成 document-index row，工作台资料候选队列为 0，
且 PASS/WARN/ERROR 仍保持 5/13/4。

工作台导入切换使用请求级 context lease：正在读取旧项目的请求结束后才关闭旧
SQL session，服务退出也会回收当前 session 和导入临时目录。器件队列、资料组、
风险提示和 review task 投影只在一个项目 context 内建立一次；代表 fixture 的
50 次重复 task 读取从约 0.086 秒降到 0.0016 秒，state/detail/prep JSON 保持等价。
并发 AI 问答也不会共用同一 ORM Session 或交错 fake-client 回合。这些是服务
正确性和响应开销改进，不改变任何电气 PASS/WARN/ERROR 结论。

真实浏览器回归还保留两套明确口径：mixed-controller 的 25 个组件产生 45 条
原始审计任务，但按 BOM 身份、规则和根因合并后是 20 个 reviewer workload
group。原始任务不删除；CSV/JSON/annotation 仍可逐条导出。评审者的新决定使用接受风险 / 误报 / 已解决 / 重新打开，按 stable finding key 保存在后端；旧接受/豁免明确标为旧版，含义不自动转换。浏览器刷新和确定性重跑后保留适用决定，输入或评审依据变化时需复核，原理由保留；人工状态不改写机器结果。

签核证据 readiness 是第三个独立口径。隔离 fresh checkout 未取回本地 PDF 时，
公开 mixed-controller 包有 11 个 datasheet page token 缺少本地来源，影响 16 条
L1 任务。运行三器件 public evidence pilot 后降为 7 个 token / 11 条任务，但仍显示
`blocked`。因此暂不新增 power/reset/clock 规则。这表示交付包尚不能完全离线复核，
不表示确定性电气结果被推翻。

## Q3. 哪些数据进向量库，哪些进关系库？为什么这样分？

- **关系库（SQLAlchemy，SQLite 与 PostgreSQL 同套表结构）**：位号、引脚、
  网络、BOM 身份、审核过的器件档案——强 schema、要做 join 和位号校验的数据。
- **向量库（Chroma 本地持久化）**：规格书长文本切块——无固定 schema、需要
  语义检索的数据。每个切块带 `{来源 PDF, 页码, 器件}` 出处元数据。

**位号 + 型号是两库之间的关联键。** 混存会让位号查询和参数引用都失去可信度：
规格书文本进关系库没法做语义检索，位号进向量库会失去精确校验。

实测链路：`l78.pdf` 切成 157 块入 Chroma，检索"absolute maximum input
voltage"top-1 命中第 4 页；评审规则引用的是人工审核过的档案事实
`datasheet:l78.pdf#p4`，向量检索是对同一页的独立佐证。

## Q4. AI 助手有哪些工具？为什么不让模型自由回答？

运行时工具面分两层：5 个核心查询工具 + 7 个工作台上下文/拓扑工具，合计约
12 个。核心查询工具输入输出全部经 Pydantic schema 校验：`list_components`、
`get_component`、`get_nc_pins`、`search_datasheet`、`run_component_validation`。
工作台路径再增加器件/网络上下文、网络搜索、项目拓扑摘要、公开文档覆盖和
已审核档案证据定位等工具，用来回答 Allegro/PST 工作台里的上下文问题。

模型自由回答会编造位号、网络名和参数。强制走工具意味着每条回答都有查询
和返回值，可审计、可复现。关键设计在"未命中"分支：问一个不存在的 `U999`，
工具不会编一个，而是返回 `found=false` 加上最接近的真实位号候选；没有加载
设计或没有器件档案时，验证工具返回"未配置 / 无档案"，而不是编一个结论。

回答按三档可信度标注：

- **L1 确定性**——通过/警告/错误结论只能来自 Python 规则和验证器，模型可以
  解释它，不能推翻它。
- **L2 有出处**——规格书问答只有携带页码级检索证据（如 `datasheet:l78.pdf#p4`）
  才标这一档。
- **L3 人工确认**——没有档案、没有检索证据，就留在人工确认区。

## Q5. 怎么防止编造位号和规格书参数？

三层合同，不是一句提示词：

1. **工具层**——未知位号返回结构化未命中 + 候选项，工具从不编造。
2. **输出层（位号防护）**——每条对外文本都用正则扫描位号形状的词
   （`U1`/`R10`/`J5`），对照解析出的器件台账校验，未注册的包裹成 `⟨?U999⟩`
   再显示。
3. **报告层（证据台账）**——没有 `sch:` / `datasheet:` / `rule:` 出处标记或
   结构化 `evidence_chain` token 的评审发现，写报告前直接丢弃；Markdown/HTML
   渲染入口也会重复执行证据过滤，并在拿到注册表时重复执行位号防护。

回归基线持续盯防：5 个公开仓库 / 6 个 KiCad 工程 / 1707 个器件 / 437 条
评审发现的公开评测包里，"未验证位号包裹数"和"因缺证据被丢弃的发现数"两个
硬指标都锁定为 0 才算通过。

## Q6. 它明确不做什么？

- 不做 PCB layout、SI/PI、EMC、热、仿真和时序收敛
- 不解析 `.brd`、boardview、布局布线和 PCB 几何
- 不做 PLM、生命周期、价格、库存和供应商风险
- 不做实时 Cadence/Allegro 插件——消费的是导出文件
- 不用任何公司内部硬件数据，即使脱敏
- 评测包是回归冒烟，不包装成专家准确率基准。新增的 seeded-defect benchmark
  提供 mutation-testing 风格的内部召回冒烟数字。当前版本化矩阵覆盖 capacitor、
  resistor、MOSFET、diode、I2C mux、DCDC buck 六个 family，共 7 个既有变异案例 /
  recall 6/7 / 0 个无法解释的新问题；这里的 false positives 是相对 clean baseline
  的新增 delta，不是总体误报率，更不是人工金标准确率。未检出的旧 Buck 案例只改为 GND_OUT 网名，并未接到转换器地；单独新增的实际地连接故障案例检出 1/1，未篡改旧矩阵补分

已知限制与后续方向：人工标注的判定准确率校准集、原理图侧网络拓扑解析器
（解锁 fanout / 连接端点类规则；网名级的命名策略检查已能读取 KiCad `.kicad_sch`
显式标签，也已在 Allegro 网表路径落地）、
企业 EDA 环境适配。原则是先窄而真，不为覆盖率把弱证据包装成硬结论。

## 通用电容、电阻检查中的通过代表什么？

电容耐压按两个端点的电压差比较，而不是单端对地电压的最大值。
电阻功耗需要两个端点和阻值，功率裕量还需要额定功率。缺端点数据或
额定功率时不能作为通过；当前接口以 UNKNOWN 明确提示待补资料；空检查集也为 UNKNOWN，
只有不适用检查时为 NOT_APPLICABLE，两者均不进入通过数。

通用电容耐压／电阻功耗现在需要显式确认的两端最小/最大电压、共同参考网络和相同工况，
网名及旧 voltage_hint 仅作候选。只有典型值、参考关系未知或缺确认时为 UNKNOWN。
可用 `--voltage-facts` 或工作台“已确认电压事实”上传，格式及公开样例见
[电压事实说明](product/voltage-facts.md)。

这只完成限定 DC 范围比较；动态应力、极性、温度降额不在通过含义内。
其他器件族仍使用旧推断路径；结果、严重度、证据、人工处置的完整分离仍在实施中，
不能将现有 PASS 当作完整电气签核。


## 为什么还有 status，同时又有 result 和 severity？

`result` 表示检查通过、不满足、未知或不适用；`severity` 表示错误、提醒或信息。
例如缺关键输入可为 UNKNOWN + ERROR，不代表已经证实设计违规。旧 `status`
仅作兼容显示，不能代替这两条轴。历史 status-only 报告需原输入重跑；原值保留，
不会自动猜成新的通过结论。人工豁免也不改写机器结果。

[检查结果合同](product/assessment-contract.md)列出序列化、迁移、统计分母和未完成门槛。
白色工作台与离线导出均能核对这些字段；已生成记录数不等于全板覆盖率。


## 为什么 XL1509 现在显示档案已隔离？

源码核对发现旧档案将随 VIN 变化的 EN 上限压成45 V，并把条件电感推荐值
当作全局范围。错误字段已纠正，但独立工程复核尚未完成，因此先从自动执行
目标中排除。它仍显示在队列中等待复核；更少的 ERROR 不能解释为电路已修好。
详见[XL1509核查记录](product/xl1509-source-audit.md)。


### 中文紧邻位号、五位数字位号与 DDR4 如何区分？

位号防护按 ASCII 标识符边界检查，因此 `检查U999是否接地`、`U10000` 中未登记的对象会显示为 `⟨?U999⟩`、`⟨?U10000⟩`；真实登记对象保留。完整网络标识符不会被拆成位号片段。DDR2–DDR5 在普通说明中作为技术词保留，明确的“位号DDR4”及工具 `refdes` 字段仍须查到当前设计对象。重复处理不会重复包裹。

这只是对象身份防护，不能证明 AI 声称的电压、参数或工程结论正确。正式结论的证据/属性校验及零工具回复边界仍待完成。


### 有真实位号和来源 token 的 AI 回答就是已核验结论吗？

不是。当前聊天合同明确返回 `claim_verification=unverified`，解释、工具来源、确定性检查和人工决定分别显示。位号查得到、来源 token 由工具返回，都不能证明模型声称的参数值、单位或适用条件正确。测试中的模型使用真实 U3 和真实规格书 token 声称“900 V、PASS”，其文字仍属未核验解释，正式检查、档案和 CSV 导出保持不变。

本回合没有可用工具结果时，Runner 不展示模型原文，返回未产生新检查结论的固定提示。未知工具、执行错误、未配置工具不算可用结果；“没有找到该器件”属于实际查询结果，可以解释。工具轨迹不再用已有器件档案补齐空证据。此边界已通过离线假模型及真实 Runner/API 验证，尚不等于任意自由文本的语义核验。


### MOSFET 和三极管耐压是否还直接相信网名？

Vgs/Vds 和 NPN VEBO/VCEO 的直流数值子检查已改用确认电压文件：两个端点须有同一运行模式、共同参考域及完整 min/max，额定字段须有有效数值和来源 token。网名、未确认的 voltage_hint、典型值或跨域电压不能让这些检查通过。范围整体超限才确定违规；只跨越边界时保留 UNKNOWN，不臆造端点相关性。缺引脚仍是连接错误，相应耐压计算显示无法评估。

公开合成的高侧例子声明 gate=58 V、source=48 V，得到 Vgs=[10,10] V；这仅对照现有档案的直流数值界限。VCEO 比较不证明基极开路适用条件，所有这类数值 PASS 都不代表开关波形、温度、电流、SOA 或功能正确。PNP/未知极性不套用 NPN 规则。其他器件族仍有启发式电压路径，迁移尚未完成；档案本身也未因这些测试而获得独立工程批准。


### TVS 的直流比较通过，是否代表钳位有效？LED 有电阻是否代表限流合格？

都不能这样推断。二极管反向电压与 TVS 工作截止电压现使用同模式、同参考域的确认范围；缺范围、额定值或字段出处时 UNKNOWN。TVS 的数值比较不覆盖浪涌、钳位波形或能量能力。两端同一已解析网络是独立连接问题；AGND、CHASSIS_GND 等不同名字不能自动视为同一电位。单向 TVS 使用工作截止字段及相应标签，而不是把它描述成绝对最大值。

LED 正的阳极减阴极电压只证明当前偏置方向，不证明点亮。零/负偏置可能属于关闭状态；未建模预期状态时不据此宣称接反。邻接电阻只是限流候选；串联关系、驱动方式、工作电流和器件能力未核验时限流 UNKNOWN，没找到电阻也不能排除恒流驱动。此处没有实现完整 LED 驱动或 TVS 浪涌模型。


### 供电、反馈和使能引脚还会按网名或标称值直接通过吗？

通用引脚电压检查现要求已确认的直流 min/max，并绑定档案地引脚实际连接的网络；地引脚缺失或连到多个未绑定域时 UNKNOWN。名字中的 12V/5V、voltage_hint 和典型值都不能建立合规范围。明确声明“相对该参考网络”的输入可直接使用，无须猜一个参考地零电压；若已有相互冲突的参考记录，则不能忽略。

完整建议范围或绝对上下界只能证明对应数值子检查；整个范围超限可确定违规，跨越边界时保留 UNKNOWN。标称 5 V 不自动意味着 4.8–5.2 V：公开合成 L78 样例的输入 [11,13] V 可完成已有范围比较，输出 [4.9,5.1] V 因档案仅有标称值仍 UNKNOWN。空限值或无来源不能通过，字段矛盾要先复核档案。地引脚显示通过仅表示已连接，不表示零电位、各地等电位或电路功能正确。

本次没有批准新的厂商限值，其他器件族仍有待迁移路径，不能据此宣称所有供电或整板检查已可信完成。


### 为什么 MCU 供电引脚与组件级供电检查会给出相同结果？

MCU VDD/VDDA、VBAT，I²C mux VDD，以及连接器电源检查现复用同一份引脚范围评估，保留各自检查名，但不再分别按网名或标称值重算。缺确认电压、参考地、完整范围或引脚出处时，组件级检查也不能通过；缺引脚/未连接仍是连接错误。建议工作范围违规与绝对数值界限违规分别保留 WARNING 和 ERROR。

公开合成 MCU 样例把名为 +3V3 的网络明确声明为相对 GND 的 2.5 V；数值比较采用 2.5 V 和档案现有 [2,3.6] V 范围，而不采用网名中的 3.3 V。这只证明有限 DC 范围比较，原样例的 SWD 接错错误依然保留。当前并未重新批准档案字段、证明 MCU 完整工作条件，或完成复位/BOOT0/I²C repeater/驱动器的全部逻辑模型。


### 控制脚接了电阻、电容或地，是否就代表默认逻辑有效？

不能。MCU NRST/BOOT0、I²C repeater EN、移位寄存器 CE 现列出实际连接网络、邻接器件和两端 R/C 支路候选。支路另一端的确认电压不会自动传播为本脚电压。即使本脚有确认 DC 范围，也不等于具备逻辑门限、采样条件、驱动能力、RC或上电时序模型；缺这些模型时功能仍是 UNKNOWN。

引脚缺失/未连接保留连接错误；已连接的控制脚可以在独立连接检查中 PASS。没有外部邻接器件时不直接断言悬空，因为尚未排除内部上拉或其他工作方式。此处没有新增完整的逻辑功能模型或批准器件参数。队列标题现在优先显示实际失败项，避免把同器件上的未知描述放在“必须修”标签下。


### 栅极驱动器 VB 很高，就代表浮动电源超压吗？

看 VB−VS，不能把 VB 直接当作相对全局地的供电电压。公开合成样例声明 VB=36 V、VS=24 V，差值为 [12,12] V；这里只比较现有档案的 25 V 数值上界。VB=60 V、VS=24 V 时差值 36 V，可确定超限；跨界区间、缺确认范围或不同参考域保留 UNKNOWN。负向工作状态不由这个单上界模型放行。VCC 使用与通用引脚相同的确认范围与实际参考地。

自举支路仍需另外核验二极管身份/极性、耐压、动态应力和充电条件，不能仅凭 SS34/SS36 等型号猜额定值，也不能从高侧网络名推出整个周期的反向应力。本项列出支路候选并保留功能 UNKNOWN；二极管自身的端点耐压比较单列。没有因这项数值检查而批准档案或证明自举工作正常。


### 关闭服务后，人工处理记录还能恢复吗？输入变了会怎样？

现在可用 `serve-workbench ... --review-db data/reviews/public-demo.sqlite` 保存本地评审日志。保留同一份输入路径和日志路径后重启，人工状态与理由可恢复；不配置此选项仍只保存在本次服务内存，白色页面会明确提示。实际 CLI 进程退出/再启动已验证恢复豁免；改变相关确认电压后变为“需复核”，原理由仍在，机器 UNKNOWN 没有被改成 PASS。日志本身不持有原始输入；上传后须在“导入”页显式保存项目，受管理输入才可供跨重启重开与搬迁。保存后使用日志和相邻输入目录，或完整备份ZIP，不能只搬日志。

人工状态、历史事件和运行快照事务提交；测试覆盖批量失败回滚、提交前子进程退出、旧写入者拒绝及导入激活失败恢复旧项目。旧页面不能用旧运行 ID 覆盖新运行。已登记局部规则可保留无关组件变化后的决定；其余依赖暂用较宽项目快照，可能多要求一次复核。保存/重开与CLI、白色页面完整备份及独立副本恢复已实现；完整逐项依赖、其余输入范围和目标环境验收仍未完成。技术合同和使用方法见 [本地评审日志](product/review-journal-v1.md)。


### 为什么评审保存或重跑返回 409？

同一 SQLite 日志已被另一个服务实例推进，或浏览器携带旧运行 ID，当前写入者已过期。409 表示状态冲突；普通参数错误仍返回 400，存储故障仍返回 503。旧服务不能用重跑覆盖新服务的决定；先停止旧实例，再用相同来源及日志重新启动。仅刷新旧服务的浏览器页面不足以更新服务持有的日志版本。


### 移位寄存器 OUT2 是编号最大的输出，就能认定为正确末级吗？

不能。OUT 数字只是一种命名，不声明预期顺序或接收端。串行输出实际到达同型号器件 DS 引脚时，当前检查只对这段已解析连接返回 PASS，不证明时序、信号完整性或完整链路功能。没有后级且未声明预期链路时返回 UNKNOWN／需复核；输出脚缺失或未连接仍是连接 FAIL。旧版根据编号推断的“末级通过”和“中间级错误”都已去除，规则版本升为 2。完整链路期望合同仍待建立。


### Buck 的输出网名和二极管型号还能决定通过吗？

不能。电感另一端叫 P1V8、+12V 或 GND 都不证明输出角色；固定输出型可核对实际反馈脚所在网络，等标称电压不能替代连接。电感接到转换器档案地引脚的同一实际网络仍报连接 FAIL，改叫 GND_OUT 但没有实际连接则不等同接地。续流二极管候选使用转换器实际地引脚核对回路；多个不同地网不自动视作等电位。即使路径存在，缺少已绑定档案的类型、极性、额定值和工况时功能仍 UNKNOWN，SS34/1N4007 等字符串不单独证明适用或不适用。同步型档案声明无需外接续流二极管的现有范围未扩展为整体功能通过。


### BOM 同一位号出现两次时会选第一行吗？

不会。重复位号从唯一匹配和自动档案目标中撤下，全部原始候选保留在 `conflicting_rows`；界面列出文件、物理起始行、Value/MPN/厂商，显示身份未确认。IC 档案检查、通用阻容回退和显式档案工具调用都被阻断，产生 UNKNOWN／需复核。无冲突器件仍可执行独立局部检查。当前拓扑规则尚无精确依赖声明，因此只要项目存在重复位号身份阻断，就保守暂停全项目拓扑结论，保留解析引脚观察；不能把这个保守范围称为精确隔离。修正原 BOM 后重跑可重新匹配；旧人工决定是否适用仍由评审指纹控制。明确 MPN 的单行冲突已阻断；Value、额定值、封装等其他字段及界面内确认仍待实现。CSV/TSV 来源行按物理记录起始行计算，跨行引号字段和空行不会再把后续冲突定位到错误行。


### 旧豁免失效后，在哪里查原理由和运行？

白色新版“问题清单 → 查看处理历史”按当前来源项目分页展示人工更新、输入变化及问题撤下。需复核事件保留旧状态和原理由；运行、问题键和旧/事件时指纹可展开。撤下不会显示为人工已解决。刷新历史返回第一页，读取失败可重试；它不修改机器结果。服务页面导出的新离线报告已封存当前项目完整历史及历史运行清单；普通CLI独立报告没有服务日志历史，会明确说明。内存服务只有本次服务历史，指定 --review-db 才能跨服务恢复决定；原始输入还需显式保存项目。详情见下文离线历史与受管理项目说明。


### 网表声明 L7805、BOM 却填 L7812，会选哪一个？

不选择来源优先级。Telesis 的 $A_PROPERTIES 及 PST primitive body 中明确名为 MPN、Manufacturer Part Number、Mfr Part Number 的属性会保留原文及记录定位；BOM 明确 MPN 不同或网表声明互相矛盾时，相关身份保持 UNKNOWN／需复核，自动档案和相关拓扑不会以任意一份为准。大小写、首尾空白可作文字规范化，其他差异（包括后缀）不靠相似匹配消除。PART_NAME、device name、Value 等库/器件标签不自动当作 MPN 声明。

若 BOM 未填 MPN，不虚构一条“不同 MPN”；但其 Value 不能绕过网表明确身份、选中未声明该身份的器件档案。即使手工指定档案，正式验证入口仍会检查声明身份。档案列出的别名仅用于绑定范围检查，不证明所有别名版本的数值和工况已审核。修改原输入后重跑可以重新匹配；界面内消歧/确认、其他身份字段和额定参数仍未完成。

PST 重复 primitive 定义或同一属性不同字面值会明确拒绝导入，不让后值覆盖前值；完全相同的重复属性仍可读取。Telesis 明确 MPN 属性指向不存在位号时也报导入错误。这里只说明当前解析子集，不承诺所有 Cadence 版本/导出变体。


### 能确认某次运行读取的输入和档案版本吗？

新建本地服务运行会保存输入/版本清单，可按运行 ID 从 `/api/workbench/review-runs/{run_id}/provenance` 下载；加 expected_project_id 可拒绝项目切换后的旧请求。清单记录实际读取文件的原始 SHA-256、大小和路径、实际档案模型与绑定、已发出检查的声明规则版本。历史清单不随当前文件改变；旧运行未记录时明确返回 not_recorded。日志写入失败会同时回滚运行清单和状态/事件。

这份 JSON 不包含原始文件，不等于完整项目备份，也不能单凭哈希恢复资料。读取集合包含为匹配而扫描的候选，实际绑定另列；不自动打开所有链接 PDF。白色页面的问题清单/导出页提供本次清单下载，历史详情可按真实运行下载。新离线 HTML 自带导出清单，断开服务也能下载；旧快照缺失会明确提示重新导出，不补算历史。完整保存/打开/搬迁/恢复仍待完成。公开混合样例本次记录 32 个读取文件、7 份使用的档案模型、8 个组件绑定、146 条检查；这些是合成演练范围，不是工程审核准确率。

### Value写25 V，独立额定列写16 V，会用哪个？

通用电容/电阻验证不设置来源优先级。CSV/TSV及现有窄XLSX读取器保留已读原列名、列序号和值，重复列也不被DictReader的覆盖行为隐藏。对明确识别的 Voltage Rating / Rated Voltage / 额定电压 / 耐压，以及 Power Rating / Rated Power / 额定功率，和Value（含重复Value/Part/名称列）中的同类额定量一起核对：冲突、错误单位或无法解析的已识别额定字段使相关解析/裕量检查UNKNOWN并需复核，显示原文与来源列。连接观察、其他器件检查仍保留；电阻两端事实完整时仍可显示独立DC功耗估算。

只有一份无冲突额定值时可直接使用该列；例如仅额定列16V、已确认20V应力会FAIL，不能因Value未带耐压而忽略它。25V与25000mV、1/4W与250mW按精确有理数归一对应，不取最大值，也不靠近似字符串消除差异。单位明确支持V/v、mV、kV和W/w、mW；功率可为分数，未知单位/复杂额定表达式不猜。列头明确带单位时可解读纯数值；列头和单元格都不带单位时不默认SI。未知其他列保留，但不自动当作电气事实。XLSX仍沿用窄表读取范围，本轮不增加公式计算、任意表头或完整原生工作簿语义。

已匹配BOM的额定来源同时保留在组件元数据中，省略BomRow参数不能绕过冲突；重建/重新应用已修正输入会移除旧来源。三个受影响生产者版本升为2。已登记局部指纹使用归一额定前提，保留源列/位置作追溯；实际额定变化会要求复核，测试中的独立Notes列修改保持原豁免。所有规则的精确依赖仍未完成，厂商/封装/其他额定字段冲突也未因此自动解决。

### Windows复验包是否表示Windows/Cadence已经验收？

### Capture引脚表的NC列为空会被当成没有NC吗？

不会。空值、未知值或损坏CSV会拒绝整份可选引脚表，并报告原文件/起始物理行号。Tcl导出脚本在NC getter失败时可能保留空值，不能据此推导“没有NC”。只接受明确的0/1、false/true、no/yes（大小写不敏感），缺refdes或pin_number也拒绝；请核对导出，或暂不附这份可选输入，不要自行填0。导入失败保留原活动评审。解析记录新增source_line，跨行字段和空行不再错算报错位置。未知引脚类型仍保留为未分类，坐标缺失不猜；独立Markdown报告列出未分类数，零提示不再声称所有输入均被驱动。这不证明多单元/层级/任意EDA版本的完整引脚兼容性。

### 上传不同类型的同名文件会怎样？

### 已保存项目怎样重开，旧理由会丢吗？

### 白色页面在哪里保存和打开项目？

进入“导入”页上方的“保存与重开”。带--review-db的本地服务可保存当前项目，查看项目名/ID/输入版本，点击打开后切回审查页。保存不会把人工处理改成机器PASS；重开沿用日志历史。列表失败可刷新重试，过期运行会显示错误并要求核对当前项目。离线报告或内存模式只显示说明，不会假装保存。完整备份包已支持CLI；页面备份/恢复已接入；空启动图形化选择仍未实现，日志与旁边.inputs目录都要保留。

### 怎样完整备份已保存项目并在新路径恢复？

先在白色页面保存当前输入，再执行 `uv run hardwise backup-projects --review-db /path/review.sqlite --output /path/backup.zip`。恢复用 `uv run hardwise restore-projects /path/backup.zip --destination /new/restored`，再按返回的journal路径和保存ID执行--open-project启动。目标目录和输出包都必须是新的，不覆盖原项目。备份使用SQLite在线一致性副本，附带已引用当前/保留输入版本、确认事实、档案及日志历史；失败保存留下的孤儿快照不随包。

恢复会核对成员/哈希/数据库/引用，并试建当前项目；损坏、越界/重复路径、符号链接、未知版本拒绝。强制退出留下restore-incomplete标记时不能打开半项目，请保留该目录，改用同一原备份恢复到另一个新目录。校验哈希不是签名或工程批准；未被拥有的外链PDF不自动随包。没有先保存的旧项目命名空间列在source_unowned_project_ids，只含日志历史，不能据此重建设计。历史记录仍保留，不把需复核变成通过。

### 能在白色页面下载备份、上传恢复吗？

坏包/过期运行/超限上传会显示错误；失败不会替换当前评审。macOS/Linux与PowerShell命令可分别查看，真实Windows执行仍需实测。离线报告及内存模式不能操作备份；完整包不能替代外链原文、人工批准或工程验收。

### 保存项目时进程突然退出，会把上次保存覆盖成半个项目吗？

本机公开L78实验已验证四个明确边界：输入发布前、发布后/数据库提交前、目录写入但未提交时退出，重开仍是上次完整保存；提交完成后退出，则重开完整新版本，项目ID与旧处理理由保留。测试先改变BOM原始字节，再删除原来源重开，逐字节对比所恢复旧/新版本，并确认备份不混入未提交快照。

这些是实际子进程os._exit验证，不代表操作系统断电、任意文件系统或Windows/Cadence均已通过。退出可能留下未引用快照/暂存目录；不会自动当项目加载，也未加入自动删除逻辑。原始输入与SQLite不能被当成单个文件事务，仍须保留完整项目备份。


### 离线 HTML、JSON 或准备包含有 PDF token，是否意味着原文已随附？

不意味着。证据包v2分别记录 `source_audit` 和 `original_delivery`：前者是有时间戳的本机路径存在观察，不核验文件内容、版本或人工批准；后者明确报告未附带PDF原文，列出缺少原文的引用。允许导出，接收者需另行获取并核对原文。链接和未定位来源列为待核查，旧报告未记录的轴显示未知。CSV、EDA批注、项目/组件准备包与白色离线页面保留这个边界。兼容字段 `signoff_ready` / `signoff_evidence_ready` 不再产生 true，不能作为签核许可；新消费者应读取两个独立轴。项目备份ZIP的受管理输入与这里的报告附件状态是不同合同，不能把保存的输入快照当作所有引用PDF的归档。


### 关闭 Hardwise 服务后，能否继续查看原始人工理由和处理历史？

在白色页面“导出”中选择“下载离线评审包”。单文件HTML封存当前项目的检查状态、人工决定、完整处理历史和本项目历史运行清单；项目/运行已变化或日志被其他进程修改时拒绝生成，要求刷新或重启，避免混合状态。SQLite历史与运行清单从同一已提交快照读取，其他项目不会混入，导出不新增运行或事件。

离线页面只读；问题清单可以翻页查看历史、下载对应历史运行清单。未记录的旧运行保留缺失说明，不从当前文件补算。普通CLI生成的独立报告没有本地评审日志，因此显示“未封存处理历史”，不能将其当作含历史的交接包。报告不附带PDF原文、不恢复原始输入，不替代项目备份。公开25事件案例已在原API进程退出、端口关闭后通过静态文件预览验证；当前浏览器工具禁止file协议，尚未据此宣称目标Windows双击打开已验收。


### 同一行有两个 MPN、厂商或封装列时，Hardwise 选哪一个？

不按列顺序或别名优先级解决矛盾。CSV/TSV和现有受限XLSX读入器共同核对所有已识别身份列；同一维度的非空值只去首尾空白并忽略大小写，其他差异保留为待确认冲突。原文件物理行、从1开始的列号、原表头和原值保留在原因中。冲突位号不进入已匹配BOM，不绑定档案，身份相关引脚/数值检查仅返回UNKNOWN；其他可判断的器件检查继续，尚无精确依赖的拓扑规则仍按已有项目范围保守暂停。修正后重新导入可解除阻断。

识别的MPN列包括MPN、Part Number、Manufacturer/Mfr Part Number、制造商料号、厂商料号；厂商列包括Manufacturer/Mfr/制造商/厂商/厂家；封装列包括Package/Footprint/封装。XLSX现在也从原始列读取MPN和厂商，不再无声丢弃。独立的suggest-validation-targets命令即使没有网表也执行同一冲突检查，矛盾项不会出现在matched-only的可执行绑定中。空白列不与有值列冲突；不会自动把TI与Texas Instruments、TO220与TO-220等别名认作等价。这里检测的是同一BOM记录内部的明确身份列，不等于已核验单列封装与网表封装、供应商料号或任意非标准表头。


### Quantity 和 Qty（或两列同名数量）互相矛盾时怎么办？

CSV/TSV/现有受限XLSX核对所有识别到的Quantity、Qty、数量列。不同的非空整数不再按列顺序选取，声明数量留空，BOM不再显示清洁；结构化quantity_column_conflicts保留物理行、原始列号、表头和值。组件详情和导出页显示数量未确认，JSON、CSV/批注、项目/组件准备包及BOM intake报告保留来源。

这是一条BOM数据诊断，不是器件身份或电气故障：身份和电压依据明确的器件检查可独立PASS，数量警示仍在。目录自动选择BOM时把这项冲突计入不一致数。1、01、1.0视为相同整数；空白补充列不构成冲突；不支持的非整数/文本计数仍报解析错误。明确的0与未知不同，报告保留0。重复给Design附加BOM时清除已失效的旧数量属性。

普通旧快照未记录该核对时显示未知，不能把“没有字段”当作“数量一致”。保留了原CSV表头归一化的Qty.和MPN.等兼容性，避免新读取器静默忽略原本支持的列。位号列互相指向不同器件属于另一种归属歧义，正在等待用户选择隔离范围，尚未修改该行为。


### 修改远处器件，为什么有些控制脚决定可以保留？

NRST、BOOT0、I²C repeater enable 和 shift-register clock enable 的第2版观察规则，现按实际控制脚及其直接网络邻域判断旧决定是否适用。范围包含器件/档案、实际选中的控制脚、网络节点、直接邻接器件及其端点电压与参考域事实。远处独立器件变化可以保留决定；直接支路、电压事实、档案或控制脚选择变化会转为需复核，保留原理由。连接观察仍不证明逻辑功能正确。

旧版曾使用全项目范围的决定会在首次升级重跑时要求复核；相同输入再次重跑不会重复追加同一失效事件。运行清单记录 `hardwise.review_dependencies.v3`；旧清单没有该字段时保持未知，不补写历史。这个版本是声明的依赖合同，不是软件代码签名。其他拓扑和未知规则版本仍使用全项目保守范围；直接邻接器件采用完整语义快照，已审查范围已排除BOM行号/数量，其余元数据和未审查规则仍可能触发较粗复核，A10 尚未全部完成。


### “接受风险”和“误报”有什么不同？旧豁免会变成误报吗？

接受风险表示人工仍认可这项问题，但愿意接受其风险；误报表示人工判断此项不适用或判断有误。两者以及已解决都必须填理由，机器检查结果不变。原 accepted/waived 只显示为“旧版接受／旧版豁免”，保留状态码、理由和历史，不推断新分类。你可在复查后主动选择新决定，这会追加事件；不会覆盖旧历史。相关输入变化时，新旧处理都可转为需复核，保留原状态和理由。

CSV/JSON/EDA批注保存 accepted_risk/false_positive 等明确代码，Markdown附中文名称；摘要分别计数旧版与新类。旧值可读取，但旧API调用提交新的accepted/waived会返回422且不写入；页面只提供明确的新分类。旧程序不认识新状态时会拒绝读取，不承诺降级；请保留升级前完整备份。详见[人工处理状态合同](product/reviewer-status-v2.md)。


### 仅调整BOM行序或数量，会撤销已经处理的电气问题吗？

对已审查版本的局部数值/引脚检查和四类控制观察，不会仅因BOM行号或数量变化撤销决定。数量不是当前这些检查的电气前提；它也不会被推断为DNP或装配状态。原始字段、数量冲突/数量核对提示、输入文件哈希和运行清单仍反映新输入，不忽略新BOM。Value/身份、已确认电压、连接、直接控制支路、档案或规则的相关变化仍会使旧决定需复核。

未登记规则/版本及其他拓扑检查继续保守使用项目快照，数量仍可能触发它们的复核，不能推广成所有规则均不依赖数量。依赖合同升级到v3时，受影响旧决定首次需复核，原理由和历史保留；重新选择明确处理后，仅行政字段变化会保留该决定。相同输入再次重跑不会重复追加同一失效事件。A10完整逐项依赖仍未完成。


### 有了人工验收表，是否就算完成档案批准与同行试用？

不算。[人工复核与试用材料](product/peer-acceptance-v1.md)只提供固定字段核对、独立标签/样本清单、两轮实际会话和逐项归因的记录入口。当前5份档案244字段逐项值/定位及源哈希匹配，但人的决定/独立复核仍空；真实参与者和试用记录仍0。空白不是0耗时或UNKNOWN标签，愿意再用不算实际回用；运行时不读取这些表，也不会自动升级READY。


### PDF引用路径无法检查时，是否会阻止离线报告？

不会因已观察到的路径OSError中断。来源核对依次检查候选路径；普通不存在记录缺失，权限/路径检查错误且其余候选均未找到时列入待核查，不认证缺失或存在。后续候选成功仅证明路径存在，仍不证明内容/版本。所有引用PDF继续明确未随附，允许导出；机器判定与签核边界不变。公开长文件名与权限故障回归覆盖此降级；真实Windows双击和PDF版本/摘录仍需独立验收。


### 工作台打开时是否会为字体访问外部网站？

当前白色工作台入口已移除GoogleFonts预连接和远程样式表，沿用已有本机字体回退。生产构建入口和新单文件导出均不含这3个链接；公开样例浏览器实测在线5请求全部本机，离线仅加载HTML一次，随后关闭服务并设断网，25历史两页/本次与历史清单/项目MD下载均未增加网络请求。此结果只覆盖所列路径；云AI确认和默认Datasheets查询仍是独立未完成项，不能因此称整个产品绝不联网。既有冻结源码包与历史报告不会自动重写。
