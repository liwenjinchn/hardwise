# 规则目录驱动的候选覆盖合同

状态：用户已选规则目录驱动；第96已实现独立候选/结果关联合同，尚未接入生产枚举器和出口。

## Goal / Context / Constraints / Done when

- Goal：候选检查在执行结果之前建立；缺失前提或漏执行不能从分母消失。
- Context：PRD第57行要求候选、适用、完成、未知、不适用和不支持分别统计。现有CheckCoverage只汇总已产生Assessment，full_candidate_count=None；它不能证明应做的检查均已执行。
- Constraints：不把所有引脚乘所有规则；不推测不支持器件的电气功能；原档案批准、连接隔离、数值与人工状态合同继续有效。候选存在不等于适用、更不等于通过。旧历史无目录快照时明确缺失，不回填。
- Done when：版本化目录、对象绑定和逐候选状态有可复算记录；漏执行/未知/不适用/不支持明确区分；CLI/API/页面/离线/清单/评测口径一致，正常及反例全链路验证、冻结与原日志升级完成。

## 数据和统计边界

1. 每个候选有目录版本、稳定rule_id、对象身份、实例判别字段与来源。规则身份不能依赖中文显示文案、列表位置或已生成结果数量。
2. 枚举与执行分离：枚举器先按已知器件/端点/网络/关系类型建立候选；必需身份或条件不足时保留原因。不得从结果列表反推完整候选集合。
3. 适用性与执行结果分轴：适用、明确不适用、适用性未知各有证据；适用但未执行或执行缺前提不得计完成。完成仅对应有效PASS/FAIL。NOT_APPLICABLE必须有明确依据，不由缺输入推断。
4. 不支持器件/规则与未解析对象单列，列原因与已知范围，不能用虚构检查数量填补。目录覆盖范围公开，候选总数仅属于该版本目录，不声称所有工程检查。
5. 一候选多条检查结果的规则必须声明聚合关系；重复/孤立结果不能悄悄增加完成数。任何无法匹配目录的输出作为合同错误或待核条目显露。
6. 旧emitted_check_records统计保留作迁移对照；新分母使用独立版本和basis。历史缺失不补造，人工决定不因分母展示变化自动批准或撤销。

## 实施顺序与验收

1. 盘点当前规则入口、分支、动态端点/关系实例及结果ID，形成目录映射，确认漏生成路径；先只读，不改判定。
2. 建立版本化目录/候选/适用性/执行关联模型与不变量；测试无结果仍有候选、未知不消失、不适用有依据、重复和孤立输出、空项目与不支持对象。
3. 按现有规则家族逐个接入枚举和显式输出关联，覆盖DRAFT档案、连接歧义、缺电压/参考域、条件不符；禁止只接容易枚举的家族后称全目录完成。
4. 同一后端快照投影至API/CLI/报告/评测，前端只显示计数与原因；保存目录和候选快照，旧运行明确未记录。
5. 对比基线，验证候选不随PASS/FAIL/UNKNOWN改变而无理由消失，执行依赖变化可追溯；完整回归、冻结包与原日志迁移后再更新验收状态。

真实独立工程标签、档案批准、Windows/Cadence与同行试用仍需独立证据，分母实现不替代它们。


## 第96：独立合同与守恒校验

`validation/candidate_coverage.py`定义版本化RuleCatalog、结构化Candidate、原子CandidateOutcome、UnsupportedScope和CandidateSnapshot。身份由目录/规则版本、对象种类/精确身份与具名实例角色组成，与显示原因、结果和输入顺序无关；保存结构化身份后可确定性重建candidate_id。每个候选是一项原子检查，多结果规则需要先拆分明确实例，不猜聚合。

目录版本/规则/对象类型必须一致，重复候选、重复结果和无对应候选的输出均拒绝。适用性未知只允许UNKNOWN；不适用必须明确声明原因且只接受NOT_APPLICABLE；适用检查缺结果仍在分母内。计数满足候选=完成+未知+不适用；未执行是未知子集，不能再次相加。不支持范围单列，不造候选数量。空候选不产生完成或100%数字。JSON往返保留结构化身份及计数。

17个定向用例覆盖上述不变量。尚无正式目录定义、完整家族枚举或输出关联，未改assessment_coverage/full_candidate_count，也未回填旧历史。下一步按接入盘点逐族生成候选并补明确执行记录，再投影消费者；本模块完成不能称覆盖分母功能已交付。
